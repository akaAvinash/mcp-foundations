# Lesson 2.1 — JSON-RPC From Scratch

**2.5 hours · Intermediate · Prereq: Phase 1**

Everything MCP does on the wire is JSON-RPC 2.0. Understand it deeply and MCP stops being magic.

## The three message types

**Request** — a call that expects an answer:
```json
{"jsonrpc": "2.0", "id": 1, "method": "add", "params": {"a": 2, "b": 3}}
```
- `jsonrpc`: always "2.0" · `id`: correlation handle (string or number) · `method`: procedure name · `params`: arguments (object or array)

**Response** — the answer (has EITHER `result` OR `error`, never both):
```json
{"jsonrpc": "2.0", "id": 1, "result": 5}
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "Method not found"}}
```

**Notification** — a call expecting NO answer. The distinguishing feature: **no `id`**. Never reply to one, even on error.
```json
{"jsonrpc": "2.0", "method": "log", "params": {"text": "started"}}
```

## Standard error codes
- `-32700` Parse error (invalid JSON; id is null)
- `-32600` Invalid Request
- `-32601` Method not found
- `-32602` Invalid params

## Mental Model
JSON-RPC is **mail with tracking numbers**. A request is a letter with a return address and tracking number (`id`). A response quotes the same number. A notification is a postcard — no number, no reply expected.

## Internal working
The client assigns a fresh `id`, stores a pending-callback keyed by it, serializes and sends. On return it reads the `id`, looks up the pending callback, and resolves it. The pending-callback table is how out-of-order responses get matched to the right caller.

## Key Takeaways
- Three message types: request, response, notification.
- `id` is the correlation handle; its absence defines a notification and forbids a reply.
- A response carries exactly one of `result` or `error`.
- Standardized error codes let clients handle failure categories programmatically.
