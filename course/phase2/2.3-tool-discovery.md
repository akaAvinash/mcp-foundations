# Lesson 2.3 — Tool Discovery Mechanics

**2 hours · Intermediate · Prereq: 2.1, 2.2**

After the handshake, the client asks "what can this server do?" via `tools/list`.

## The catalog
Each tool in the response has:
- `name` — unique id used in `tools/call`
- `description` — natural language; the LLM reads this to decide *when* to use the tool (functional, not decorative)
- `inputSchema` — a JSON Schema describing the parameters, so the LLM knows *how* to call it

## JSON Schema essentials
`type` (object/string/number/integer/boolean/array), `properties`, `required`, `description`, `enum`, `items`.

## list ↔ call
`tools/list` says what exists and how to call it; `tools/call` (with `name` + `arguments` matching the schema) actually calls it. The `name` is the contract between them.

## Where the schema comes from
In the SDK, `inputSchema` is **auto-generated from your function's type hints**, and the `description` from the docstring. Well-typed, well-documented functions produce good schemas. (Verified: `def add(a: float, b: float)` → `a`,`b` required numbers.)

## `notifications/tools/list_changed`
If the server declared `tools: {listChanged: true}`, it emits this notification when its tool set changes, so clients refresh their cached catalog.

## Mental Model
Discovery is a **restaurant menu**: `tools/list` asks for the menu; each item has a name, description, and the choices you must specify (the schema). `tools/call` is placing the order.

## Key Takeaways
- Discovery returns a catalog: name, description, inputSchema per tool.
- inputSchema (JSON Schema) is what lets an LLM call tools correctly.
- The `name` is the contract between list and call.
- Descriptions are functional — they drive tool selection.
