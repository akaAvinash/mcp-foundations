# Lesson 2.2 — The MCP Handshake / Initialization

**2 hours · Intermediate · Prereq: 2.1**

Before any tool call, client and server complete a handshake — ordinary JSON-RPC in three steps.

## The three steps
1. **`initialize` request** (client → server): declares `protocolVersion`, client `capabilities`, `clientInfo`
2. **`initialize` response** (server → client): agrees a version, declares server `capabilities` (tools/resources/prompts, each with flags like `listChanged`, `subscribe`), `serverInfo`
3. **`notifications/initialized`** (client → server): a notification (no id) meaning "I'm ready" — only now may operations begin

## Capability negotiation
Both sides declare what they support up front, so neither calls a feature the other lacks. This lets a minimal server and a rich server both be valid, with clients adapting.

> Protocol version strings are date-based and evolve (e.g. `2025-06-18`, and newer revisions such as `2026-07-28`). Inspect your SDK rather than hardcoding.

## Session state machine
`new → initializing → ready`. Operations are only legal in `ready`. Calling a tool before the handshake completes should return a "not initialized" error.

## Mental Model
Two diplomats exchanging credentials before a summit: present papers (initialize), receive papers + agreed language (response), signal "let's begin" (initialized). No substantive work until credentials are exchanged and acknowledged.

## Key Takeaways
- The handshake is JSON-RPC: `initialize` request/response + `initialized` notification.
- Three states: new → initializing → ready; operations only in ready.
- Capabilities are negotiated so minimal and rich implementations interoperate.
- Version strings are date-based — inspect, don't hardcode.
