# Lesson 3.3 — Transports, Security & Shipping

**3 hours · Advanced · Prereq: all prior lessons**

Make your server runnable anywhere, safe, tested, and shippable.

## Transport
- **STDIO** — host launches the server as a local subprocess; talks over stdin/stdout. Simplest; no ports/auth. On STDIO, stdout is the wire — log to stderr, never `print()`.
- **Streamable HTTP** — server listens on a URL for remote/multi-client use; adds auth and network concerns. (An older SSE transport exists but is being superseded — prefer `streamable-http`.)

Decision rule: **local/single → STDIO; remote/shared → Streamable HTTP.**

```python
if __name__ == "__main__":
    server.run()                              # STDIO (default)
    # server.run(transport="streamable-http") # network
```
Verified: the SDK's `run()` accepts exactly `'stdio'`, `'sse'`, `'streamable-http'`.

## Security essentials
- **Input hardening** — every tool/dynamic-resource validates input (3.1)
- **Least privilege** — the server has only the access it needs (scope file access to a base dir; minimal DB rights)
- **Secrets** — from environment variables, never hardcoded or committed
- **Prompt injection via tool output** — external content a tool returns may contain instructions trying to hijack the LLM. Treat tool output as untrusted data.

## Testing
- **Unit tests** — call tool functions directly with good/bad inputs (does `read_file` reject `../`?)
- **Protocol tests** — run the server, exercise it through a client/Inspector

## Shipping
Structured logging to stderr; a clear layout; a README (purpose, primitives, how to run); a runnable entry point.

## Key Takeaways
- STDIO for local/simple; Streamable HTTP for remote/shared — same logic, different channel.
- Security essentials: input hardening, least privilege, secrets in env, prompt-injection awareness.
- Tool output is untrusted data.
- Tests + logging + README turn a script into a shippable server.
